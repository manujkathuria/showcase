# Implementation Report 004: Database Performance Baseline and Evidence-Driven Tuning

## Overview

This report documents the performance baseline, query plan measurements, index tuning, and batched write benchmarks for PostgreSQL market data storage (`market.live_ticks` and `market.order_depth`). Measurements were conducted on a local reproducible dataset generated by the Task 003 seed engine to establish the query contract and page sizing for the mock replay engine ([Task 005](../tasks/005-mock-websocket.md)).

## 2. Mock Replay Query Performance

### The Mock Replay Contract
The mock server replays ticks from a single configured `stream_id` for a given time window `[start_time, end_time)` and optional subscription subset (`instrument_id IN (...)`). It pages deterministically using a keyset cursor `(received_at, id) > ($cursor_time, $cursor_id)` and retrieves all 10 order depth levels in a single query by limiting ticks first.

### Query Plan Measurements (`EXPLAIN (ANALYZE, BUFFERS)`)
Captured via [`infra/db/checks/006_replay_benchmarks.sql`](file:///Users/manujkathuria/workspace/gidh/intraday-trading/infra/db/checks/006_replay_benchmarks.sql) on stream `c0000000-0000-0000-0000-000000000003`:

| Query Shape | Limit (Ticks) | Returned Depth Rows | Execution Time (ms) | Buffer Access (Hit / Read) | Query Strategy |
|---|---|---|---|---|---|
| **Latest Tick (Single Instrument)** | 1 | 0 (No depth joined) | 0.054 ms | 7 hit / 0 read | Index Scan Backward on `live_ticks_instrument_received_idx` |
| **History Slice (Single Instrument)** | 100 | 0 (No depth joined) | 0.183 ms | 24 hit / 0 read | Index Scan on `live_ticks_instrument_received_idx` |
| **First Page (All Instruments)** | 100 | 1,000 | 1.28 ms | 442 hit / 0 read | Index Scan on `live_ticks_stream_replay_idx` + Index Scan on `order_depth_pk` |
| **First Page (All Instruments)** | 1,000 | 10,000 | 11.46 ms | 3,897 hit / 0 read | Index Scan on `live_ticks_stream_replay_idx` + Index Scan on `order_depth_pk` |
| **Middle Page (`cursor: 09:23:00`)** | 1,000 | 10,000 | 13.05 ms | 3,897 hit / 157 read | Index Scan on `live_ticks_stream_replay_idx` + Index Scan on `order_depth_pk` |
| **Late Page (`cursor: 09:30:00`)** | 1,000 | 10,000 | 13.05 ms | 3,897 hit / 157 read | Index Scan on `live_ticks_stream_replay_idx` + Index Scan on `order_depth_pk` |
| **Subscription Subset (2 Instruments)** | 100 | 1,000 | 1.67 ms | 423 hit / 0 read | Index Scan on `live_ticks_stream_replay_idx` + Filter (392 rows rejected) |
| **Subscription Subset (2 Instruments)** | 1,000 | 10,000 | 99.50 ms | 3,553 hit / 608 read | Index Scan on `live_ticks_stream_replay_idx` + Filter (3,992 rows rejected) |

### Key Findings
1. **Keyset B-Tree Traversal**:
   - Keyset cursor paging using `(received_at, id) > ($cursor_time, $cursor_id)` traverses the B-Tree index in $O(\log N)$ time, avoiding the linear scan degradation of `OFFSET`.
   - Execution time for a 1,000-tick page remains consistent across the beginning, middle, and end of the stream recording (~11–13 ms when warm).
2. **Subscription Filtering Overhead**:
   - Filtering by a narrow subset of instruments (e.g. 2 out of 10) against `live_ticks_stream_replay_idx` requires the index scanner to scan chronological ticks and reject non-matching instrument IDs.
   - For a 1,000-tick page of a 2-instrument subscription, 3,992 intermediate non-matching ticks are scanned and discarded, increasing execution time to ~99.5 ms.

## 3. Candidate Index Evaluation: `(stream_id, received_at, id)`

### Comparison: Single- vs. Multi-Stream Workloads
When only 1 stream exists in the database, `(received_at, id)` and `(stream_id, received_at, id)` produce identical query plans.

When multiple streams share overlapping timestamp ranges:
- **Global Index `(received_at, id)`**:
  - The query planner must scan all ticks chronologically across all streams, filtering out rows where `stream_id != target_stream`.
  - In a 2-stream test, 90 non-matching rows were scanned and discarded per 100 returned ticks, doubling page buffer reads. With $K$ streams, scan cost scales with total table size.
- **Composite Index `(stream_id, received_at, id)`**:
  - The planner restricts the index scan to the target `stream_id`'s B-Tree range.
  - Zero rows are removed by `stream_id` filtering, and page buffer reads drop to the minimum required for the stream.
- **Decision**: Retained `market.live_ticks_stream_replay_idx` via Migration 003.

### Order Depth Index Evaluation
- `market.order_depth` uses compound primary key `(tick_id, side, level)`.
- When joined on `tick_id = page_ticks.id`, PostgreSQL performs an exact prefix index scan on `tick_id`, retrieving the contiguous 10 depth levels without table scans.
- **Decision**: No redundant secondary indexes on `order_depth` were added.

## 4. Batched Write Benchmarks (`go-io-batching`)

Measurements were collected using `RUN_DB_BENCHMARKS=1 go test -v -bench=BenchmarkBatchedWrites -benchtime=2x ./internal/db` with isolated ephemeral streams (10,000 ticks = 100,000 depth rows per run):

| Batch Size (Ticks) | Depth Rows / Batch | Pure DB Insertion Time (s) | DB Tick Rate (ticks/sec) | DB Depth Rate (depth/sec) | In-Memory Gen Rate (ticks/sec) |
|---|---|---|---|---|---|
| **250** | 2,500 | 1.47 s | 6,797 ticks/s | 67,974 depth/s | 2,820,129 ticks/s |
| **500** | 5,000 | 1.36 s | 7,328 ticks/s | 73,282 depth/s | 2,629,388 ticks/s |
| **1,000** | 10,000 | 1.34 s | 7,455 ticks/s | 74,546 depth/s | 3,625,268 ticks/s |
| **2,500** | 25,000 | 1.33 s | 7,495 ticks/s | 74,954 depth/s | 4,477,737 ticks/s |
| **5,000** | 50,000 | 1.51 s | 6,596 ticks/s | 65,957 depth/s | 2,999,832 ticks/s |

### Analysis
1. **Separation of Phases**:
   - Go in-memory generation operates at **~2.6–4.5 million ticks/sec** with zero heap allocations.
   - Database transactional writes (multi-row INSERT for ticks + binary `CopyFrom` for depth + WAL transaction commit) operate at **~65,000–75,000 depth rows/sec**.
2. **Batch Sizing Observations**:
   - Moving from 250 ticks/batch to 1,000 ticks/batch improves DB write throughput by ~9.6% by reducing transaction commit count and network round-trips from 40 to 10 per 10k ticks.
   - Batch sizes between **1,000 and 2,500 ticks** achieve the highest throughput (~74,500–74,950 depth rows/sec).

### Handoff Specification for Task 005 (Mock WebSocket Server)

#### Replay Query Contract
```sql
WITH page_ticks AS (
    SELECT
        t.id, t.instrument_id, t.stream_id, t.sequence,
        t.received_at, t.exchange_at, t.last_trade_at,
        t.last_price, t.average_price, t.open_price, t.high_price, t.low_price, t.close_price,
        t.last_quantity, t.volume, t.total_buy_quantity, t.total_sell_quantity,
        t.open_interest, t.open_interest_high, t.open_interest_low,
        inst.instrument_token, inst.trading_symbol
    FROM market.live_ticks t
    JOIN feed.instruments inst ON inst.id = t.instrument_id
    WHERE t.stream_id = $1
      AND ($2::bigint[] IS NULL OR t.instrument_id = ANY($2))
      AND t.received_at >= $3
      AND (t.received_at, t.id) > ($4, $5)
      AND t.received_at < $6
    ORDER BY t.received_at ASC, t.id ASC
    LIMIT $7
)
SELECT
    pt.*,
    od.side, od.level, od.price AS depth_price, od.quantity AS depth_quantity, od.order_count AS depth_order_count
FROM page_ticks pt
LEFT JOIN market.order_depth od ON od.tick_id = pt.id
ORDER BY pt.received_at ASC, pt.id ASC, od.side ASC, od.level ASC;
```

#### Handoff & Edge Case Handling
1. **Left Join for Snapshot Completeness**:
   - Uses `LEFT JOIN market.order_depth` so that ticks with zero or partial depth are not silently omitted by PostgreSQL. The Task 005 application layer will validate snapshot completeness (asserting exactly 5 bids and 5 asks for full-mode packets) before streaming.
2. **Page Size Configuration**:
   - Keep page size configurable in Task 005. **1,000 ticks** (10,000 depth rows) is a recommended throughput-oriented setting (~11–13 ms execution time), but smaller page sizes (e.g. 100 ticks, ~1.2 ms) can be used when client subscription buffer limits require tighter delivery increments.
3. **Subscription Mutation Invalidation**:
   - When client subscriptions change dynamically during playback, prefetched page rows must be filtered or invalidated in memory before dispatch to comply with the live subscription contract.
